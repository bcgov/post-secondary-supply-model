## 1. What DACSO v2 is — and why it exists beside the original

The DACSO matcher maintains the program-level XWALK that assigns each STP
credential program a 4-digit CIP, using the DACSO survey's program coding as
the evidence base. Its output is the **first and richest source** in
`02a-update-cred-non-dup`'s priority chain (DACSO > BGS > GRAD > APPSO > STP
fallback — a 7-column business-key join), so its CIP decisions reach
`credential_non_dup_r` and then the `LCIP4_CRED` cohort key in 02b-1 — the
P(CIP | cred, age) term of the PSSM formula — ahead of every other source.

The frozen original works, but its Part 1 XWALK maintenance is five
copy-paste per-cycle blocks plus **hand-walked recursive chains**: each cycle
an analyst filters the year's programs, joins the XREF historical links,
reads the registry NOTES, and hand-writes `PRGM_ID == <id> ~ "<value>"`
overrides (the 2021 `3119` block, the 2022 `115/9006/131/5952/9008/4960/117`
block, the 2023 `9237/1158/9810` block). The v2 script replaces all of that
with one parameterized walk, classifies every override against what the walk
actually produces, and stamps a decision trace on every credential program:

| Knowledge | Original (frozen) | v2 |
|---|---|---|
| Recursive chain chase | hand-walked from NOTES, per cycle | `resolve_hist_links()` — terminate-on-landed, max-depth 5, one pass across all cycles |
| Multi-hop chain outcomes | hardcoded `PRGM_ID ~ value` overrides | walk rule: newest program's coding wins onto the landed XWALK row |
| Dead-end lineages | one-off manual add (10493→9810, 2023) | rule: add a row keyed by the chain's last node |
| Past manual decisions | inline comments + commit history only | classified (i)/(ii)/(iii) per override; exceptions live in `dbo.T_DACSO_PRGM_EXCEPTIONS_v2_r` with rationale |
| Credential-program matching | flag columns, no trace | same passes, plus a `MATCH_RULE` on every row |

`resolve_hist_links()` is a pure function unit-tested in
`tests/test-cip-matching.R` (seam 3): the full suite is 20/20 green.

## 2. The walk semantics — now written down

The original's chain notes ("10355 -> 9855 -> 115 (update CIP and CPC to
most recent)", "10359 -> 9856 -> 9006 -> 4760 (4760 doesn't exist in XWALK,
update 9006)") encode rules that were never stated anywhere. Decoded:

1. **Direction**: walk from the NEW program along `PRGM_ID →
   HISTORICAL_PRGM_ID` links (new → old). Institutions retire and re-code
   programs; the registry's XREF records each descent.
2. **Landing**: a chain *lands* on the first node **present in the XWALK**.
   Registry-coded nodes that are not in the XWALK (9856, 4760) are mere
   waypoints — the walk continues past them.
3. **Value**: the **newest** program's coding (the walk start's registry row)
   is written onto the landed XWALK row's CIP/CPC/name — "update to most
   recent" meant exactly this.
4. **Ambiguity**: when a PRGM_ID has several outgoing links, the latest
   `YEAR_LINK_CREATED` wins; ties prefer a `PRGM_INST_CD` match to the
   originating program.
5. **Safety net**: max depth 5; cycles (A→B→A) and dead-ends terminate with
   no terminal and surface in the residual diagnostics.
6. **Dead-end rule**: a lineage with no XWALK node anywhere gets a NEW XWALK
   row keyed by the chain's last node, carrying the start program's registry
   info (the 2023 10493→9810 manual add, now a rule).
7. **NOTES**: advisory output only (surfaced in the chains CSV; never parsed).

First-run walk stats: 557 with-links programs missing from the XWALK →
**298 chains landed**, **124 in-XWALK terminals refreshed**, **43 missing
terminals added**. Every walked chain is in
`.scratch/cip-matching/diagnostics/dacso-v2-walk-chains.csv` (regenerated by
each run; `.scratch/` is local-only).

## 3. WALK_RULE and MATCH_RULE vocabularies

XWALK rows carry `WALK_RULE` (how the row got its current coding):

| WALK_RULE | Meaning |
|---|---|
| `seed_registry_recode` | seed CSV row, CIP2021-recoded on shared business keys |
| `new_program_no_link` | new registry program, no historical link |
| `auto_walk_terminal_refresh` | landed chain wrote the newest coding onto the row |
| `auto_walk_add_missing_terminal` | dead-end lineage row added at the chain's last node |
| `new_stp_program_added` | STP side joined in Part 2 (already-matched for future runs) |
| `exception_override` | the classified-exception value applied (see §4) |

Credential programs (the FinalCIPs output) carry `MATCH_RULE`:

| MATCH_RULE | Rows (first run) |
|---|---:|
| `already_matched_psi` | 2,026 |
| `already_matched_coci` | 178 |
| `new_auto_match_coci` | 322 |
| `new_auto_match_psi` | 4 |
| `inst_rule_bcit` (4-char code prefix) | 347 |
| `inst_rule_capu` (dash-strip / 4 / 3-char) | 191 |
| `inst_rule_viu` (code between "-" and "_") | 43 |
| `catch_all_code` | 460 |

| `stp_fallback` (INFOWARE taxonomy from own CIP) | 1,886 |

Totals: 5,649 distinct credential programs (identical row count to the

## 4. The override classification — the headline finding

Every hardcoded override in the frozen original was classified against what
the auto-walk actually produces (log:
`.scratch/cip-matching/diagnostics/dacso-v2-override-classification.csv`):

> **The 2022 hand-walked CIP overrides reproduce EXACTLY** — the walk
> independently derives 115→1502, 9006→1110, 131→5001, the same values the
> analyst chased by hand through the registry NOTES. Everything else differs
> only by dictionary evolution or is one genuine judgment call.

| Class | Count | Rows |
|---|---:|---|
| (i) reproducible | 5 | 115/9006/131 CIPs (exact), 3119 CPC, 9810 add (carried by seed) |
| (iii) rule-reproduced, dictionary evolved | 9 | all CPC rows — original wrote 2022-era codes ("CENG.DIP"); the walk writes the registry's current coding ("CIVILENG"). Current kept. |
| (ii) genuinely exceptional | **1** | **3119 CIP**: original 1907 (2021 NOTES-review judgment: "Education Assistant and Community Support Worker" → Human development) vs the registry business-key recode 1315 |

The single (ii) row is seeded to `dbo.T_DACSO_PRGM_EXCEPTIONS_v2_r` with a
reconciliation rationale, and the **original's value is applied** (1907) so
v2 never silently loses a past manual decision. This is the one open analyst
item from the first run.

## 5. v1-vs-v2: what the first run showed

Business-key comparison of the FinalCIPs outputs (5,649 programs each):

| Measure | Value |
|---|---|
| FINAL_CIP_CODE_4 identical | 5,571 (**98.74%**) |
| Differing | 71 (1.26%) |

Per-PEN CIP4 disagreement against the survey side (the ticket-04 validation
metric, modal-dedup denominator; the v1 probe reproduces the ticket-11
baseline exactly, validating the method):

| Table | Pairs | Disagree | Rate |
|---|---:|---:|---:|
| v1 `credential_non_dup_r` (DACSO bucket) | 107,568 | 13,869 | **12.89%** |
| v2 (auto-walk XWALK + v2 FinalCIPs) | 107,560 | 11,861 | **11.03%** |

**v2 improves on the original immediately: −1.86pp**, with no curation debt.
This contrasts with BGS v2 (temporarily 1.55pp behind pending curation of 299
borderline combinations — see `docs/bgs-v2-program-matching-findings.md` §4):
the DACSO walk resolves chains the original's blocks missed, while the BGS
residual is analyst knowledge v2 deliberately externalized rather than
borrowed.

## 6. Analyst work-list

1. **Reconcile PRGM_ID 3119** (the one (ii) exception): original 1907 vs
   registry 1315. Read the seeded rationale in
   `dbo.T_DACSO_PRGM_EXCEPTIONS_v2_r`, decide, and either update that row
   (the script applies it on rerun) or let the registry coding win by
   removing the row.
2. **Skim the walk-chains CSV** for dead-end chains (`TERMINAL_PRGM_ID` NA)
   — the residual NOTES-advisory caseload; genuinely ambiguous lineages
   stay an analyst judgment (map rule: full NOTES automation is out of
   scope).
3. The 43 `auto_walk_add_missing_terminal` rows are new-rule additions — a
   quick sanity check that the added lineages look right costs one filter of
   the XWALK v2 output.

## 7. Notes for future runs

- The script is idempotent: the exceptions table is seeded only when absent
  and thereafter analyst-maintained (the script applies whatever it holds).
- The seed XWALK still cold-starts from the 2021_23 LAN CSV with the
  registry business-key recode (the CIP2021-migration design — DB seeds are
  retired). Once a v2 XWALK is accepted as the cycle seed, the CSV path can
  retire; that swap is a future-cycle decision, not this script's.
- Ticket 16 (TRD v2) PEN-matches TRD survey respondents into the DACSO
  bucket — it consumes this script's outputs and the spine's
  `normalize_pen()`. Ticket 17's comparison harness formalizes §5.
